# 09주차 실습 · 검색·정렬·페이지네이션 게시판 개선

1,000건 인메모리 게시판 예제(`server.js`, `index.html`)를 실행·검증하고, 발견한 문제를 수정한 결과물입니다.
원본 대비 바뀐 코드는 파일 안에 `// [수정 N]`(서버), `// [수정 X]`(프론트) 주석으로 표시했습니다.

---

## 1. 실행 방법

```bash
npm install express
node server.js
# 브라우저에서 http://localhost:3000 접속
```

느린 네트워크(응답 순서 뒤바뀜) 테스트용 실행 — API 응답을 0~1500ms 랜덤 지연합니다.

```bash
# macOS / Linux
DELAY_MS=1500 node server.js

# Windows PowerShell
$env:DELAY_MS=1500; node server.js
```

> `node_modules` 폴더는 `.gitignore`로 제외했습니다. 클론 후 `npm install express`부터 실행하세요.

## 3. 개념 설명

### ① 오프셋과 커서에 적합한 화면

- **오프셋 페이징 (`LIMIT ? OFFSET ?`)**: 페이지 번호로 원하는 위치에 바로 이동해야 하는 화면에 적합합니다. 예) 게시판 목록, 관리자 페이지, 검색 결과 목록. 전체 개수와 마지막 페이지를 보여줄 수 있습니다. 단점은 뒤 페이지로 갈수록 앞의 행을 읽고 버려야 해서 느려지고, 조회 중에 새 글이 추가되면 항목이 밀려 중복·누락이 생길 수 있다는 점입니다.
- **커서 페이징 (`WHERE id < ? ORDER BY id DESC LIMIT ?`)**: 계속 아래로 이어 보는 화면에 적합합니다. 예) SNS 피드, 채팅 기록, 알림 목록, 무한 스크롤. 마지막으로 본 id 다음부터 읽기 때문에 깊이 들어가도 속도가 일정하고 새 글이 생겨도 중복·누락이 없습니다. 단점은 특정 페이지로 건너뛸 수 없고, 정렬 기준이 커서 키(여기서는 id)로 고정된다는 점입니다.

### ② 디바운스와 요청 취소의 역할

- **디바운스(300ms)**: 입력이 멈추고 300ms가 지나야 요청을 보냅니다. `InnoDB`를 빠르게 치면 글자마다 6번 갈 요청이 1번으로 줄어 서버 부하와 불필요한 렌더링을 막습니다. → 요청 **횟수**를 줄입니다.
- **요청 취소(AbortController)**: 이미 보낸 요청이 끝나기 전에 새 요청을 보내면 이전 요청을 취소합니다. 네트워크 상황에 따라 이전 검색(`Redis`) 응답이 나중 검색(`zzz`) 응답보다 늦게 도착하면 화면에 엉뚱한 결과가 남는데(Race Condition), 이를 막습니다. → 응답 **순서** 문제를 해결합니다.
- 두 방법은 역할이 다르기 때문에 함께 써야 합니다. 디바운스만 쓰면 300ms 이상 간격으로 입력할 때 요청이 겹칠 수 있고, 취소만 쓰면 요청 수 자체는 줄지 않습니다.

### ③ `limit + 1` 원리

다음 페이지가 있는지 알려면 원래 `COUNT(*)`로 전체 개수를 세야 하지만, 대용량 테이블에서는 비쌉니다. 대신 필요한 개수보다 **1개 더** 조회합니다.

```
limit = 10 → 11개 요청
- 11개가 왔다 → 다음 데이터가 있음 (hasNext = true), 화면에는 앞의 10개만 표시
- 10개 이하   → 마지막 페이지 (hasNext = false)
nextCursor = 화면에 보여준 마지막 항목의 id
```

### ④ offset · totalPages 계산식

```
offset     = (page - 1) × limit
totalPages = max(1, ceil(totalCount ÷ limit))
```

예) `totalCount = 83`, `limit = 10` → `totalPages = ceil(8.3) = 9`, 3페이지의 `offset = (3-1)×10 = 20` → 21~30번째 항목.
`page`가 `totalPages`보다 크면 마지막 페이지로 보정합니다(`page=999` → `page=100`).
